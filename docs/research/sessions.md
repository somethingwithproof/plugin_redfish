# Authentication, session limits and session cost

Research for [#22](https://github.com/somethingwithproof/plugin_redfish/issues/22), 2026-11-15. Question: for each BMC family, how many simultaneous sessions are allowed, what is the idle timeout and failure mode, is session creation logged in a way that floods event logs, and is a login per run or a cached token the better design?

**Result.** Documentation gives limits for two of four families: Lenovo XCC2 allows 16 open sessions with a default idle timeout of 300 s, and OpenBMC `bmcweb` has a default idle timeout of 1800 s and no session-count limit in the source read. HPE says only that the number is limited and that exhausting it can block management until sessions time out or iLO is reset; Dell's guide could not be read (the developer portal returned 403), and a Foreman bug report shows iDRAC session exhaustion happening with no number. The failure mode when a limit is hit, audit-log volume, and login latency are *live*. The design recommendation, which needs no live data: **one session per BMC per run, always deleted in a `finally` path, never cached or stored**, with Basic authentication used only where session creation is unavailable. Caching a token would need a new requirement and decision record, as the issue says, and the documented limits (16 sessions on Lenovo, unknown elsewhere) argue against giving a monitoring tool a long-lived slot.

## Design consequences

1. **Session per run.** One POST to the sessions collection and one DELETE per BMC per run: 2 of the request budget in [polling-cost.md](polling-cost.md). The token lives in a local variable for the run, is redacted from logs (ADR 0006), and is never written to the database.
2. **Logout on every exit path.** Timeouts, parse errors and exceptions all reach the DELETE. A killed collector leaks one session until the BMC's idle timeout (the same happens when the session POST succeeds on the BMC but its response is lost to a timeout: the collector then has no token and no `Location`, so no DELETE is possible, and repeated timeouts can fill the slots; see item 3): 300 s on Lenovo's default, 1800 s on bmcweb's, unbounded on an HPE with timeout 0. At 16 slots on Lenovo, three crashed runs per slot-lifetime is not a problem; with per-BMC concurrency of one, a leak costs one slot.
3. **Own-session cleanup (proposal, unverified; required after a lost response).** Because `Session` GET and DELETE need `ConfigureSelf`, and `Session` carries `UserName`, `CreatedTime` and `ClientOriginIPAddress` (`Session.v1_9_0`), the collector can list sessions of its own `UserName` and `ClientOriginIPAddress` and delete stale ones. Rule: after any session POST that ends in a timeout or connection error (token unknown), the BMC is marked `session_unknown`; before the next login the collector lists and deletes its own stale sessions, and if that is impossible (listing needs a session or Basic) it waits one idle timeout when known, or backs off with the ceiling in item 7, instead of retrying at once. Each lost-response event counts against a per-BMC budget (a proposal: stop after 3 in a row and report). Needs a live test per family before it is specified. It also risks deleting a second collector's session sharing the account, so the plan should say one account per collector.
4. **Basic fallback only on evidence that sessions are unavailable.** Use Basic when the service root has no `Links.Sessions` or `SessionService`, or the session POST returns 404, 405 or 501, and only over HTTPS. A 429, 503, other 5xx, timeout or connection error is overload or a transient fault: it triggers the backoff in item 7, not a Basic walk, because a Basic walk adds requests to a BMC that is already struggling. Basic costs no session slot but authenticates every request; on OpenBMC a Basic request creates a transient non-persisted session (source above). The cost of per-request authentication (PAM or LDAP lookups) is *live*.
5. **MFA.** If MFA is on for the account, Basic is rejected and session login needs a `Token` (spec 13.3.4.2); the plugin cannot supply one. The account must be configured to bypass MFA or the BMC is reported as `auth_failed`. Not settled for each vendor (*live*).
6. **Lockout.** A wrong password can lock a shared account when `AccountLockoutThreshold` is above 0. Rule: after a 401 on login, the BMC enters `auth_failed`, is not tried again until its credential or address is edited or an operator retries manually, and the health page says so. No automatic retry per run. This follows from the spec's lockout properties and is not vendor-tested. Recovery after a corrected secret: a credential edited in plugin_credentials changes its `last_updated`, which `credentials_get()` returns, so a changed `last_updated` or `provider_id` clears `auth_failed` for one attempt. A provider-backed secret (Vault and others) can rotate without any change to the credential record, so for those the plugin needs a second trigger. Option A (proposed, needs owner approval because it stores a derived value): keep a keyed digest of the last rejected password (`hash_hmac('sha256', $password, <installation secret key>)`) in the BMC row, and allow one retry per cool-down (for example 6 hours) only when the resolved password digest differs from the rejected one; a rejected password is then never sent twice. Option B: a manual retry button only. Either way, never retry the same rejected password, and a second 401 returns the BMC to `auth_failed`.
7. **Concurrency and backoff defaults.** Per-BMC concurrency 1 (the plan's value). Back off exponentially on timeouts and 5xx, starting at one collection interval and doubling to a ceiling of one hour; honor `Retry-After` when present (the header is in the spec's header table, 3639) with the same ceiling. The number of simultaneous BMCs `W` is set from #23's measurement. These defaults are proposals; none is measured.
